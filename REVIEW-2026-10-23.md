# Review 2026-10-23

This review covered the whole monorepo at v2.6.0, followed by fixes for every finding. It's based on `main` at `3f49058`. It was delivered on `feature/review-2026-10-23` as 243 signed commits, with the head at `d2cb721`, followed by one commit that adds this record. The branch changes 257 files. The combined tree passes the full gate: build, typecheck, 4,743 unit tests, 4,254 BDD tests, 147 integration tests (4 skipped), the 14 e2e tests, both linters, knip, the release-script tests, and the repo-tooling tests.

This record follows `REVIEW-2026-09-25.md` and keeps its shape: what was reviewed, what was found, what was done about each item, and what is left. The fixes required decisions D44 to D55 in `DECISIONS.md`, and D42 moved from proposed to adopted.

## How it ran

Work ran across five orchestrated workflows. The review itself was read-only: an owner read each package in full, cross-cutting lenses covered the docs, release and CI, public types, and test quality, and a completeness critic named four seams between packages that then got reviewers of their own. Every finding was verified before being kept: 156 were verified, six duplicates were merged, and one claim was refuted. The fix waves gave each slice of findings one implementing agent in its own worktree, then a cold reviewer that hadn't seen the implementation, and then a fixing agent for anything the reviewer marked as a blocker or should-fix. Slices were cut so no two slices in a wave edited the same file; where a slice needed two implementing agents, the second ran after the first.

Agents committed unsigned work-in-progress in their worktrees. After each wave, the session squashed every branch's fixup commits into the commits they amended, cherry-picked the branches onto `feature/review-2026-10-23` in dependency order, and re-signed every commit. The full gate then ran on the combined tree, and the session fixed what the combination broke before the next wave started. After waves 2 and 3, these were test pins on behaviour another slice had changed on purpose.

## Outcome

- The review confirmed 150 findings: 20 major, 98 minor, and 32 nits. 146 are fixed, 3 are partly fixed, and 1 was declined and documented. Every major finding is fixed.
- The two bugs carried over from the 2026-09-25 review are fixed: the cross-slot `$ref` in validation (validation-query-1) and faker's `not` (faker-2, now rejected at creation when generation can't honour it, D46).
- The largest clusters are closed. Recursive schemas no longer answer 500 on every request (D48). The openapi normalizer stopped mutating components shared across the dereferenced graph, so `readOnly` and `required` don't leak between uses. Multipart and form bodies reach validation and CRUD as records on every transport instead of raw `FormData` or strings (D47, D49, D52). `validateResponses` accepts valid decimals, stops hiding its own errors behind `INVALID_RESPONSE`, and no longer spends about a minute per route compiling the Stripe spec (D49).
- CRUD writes and callbacks now settle in a new core hook, `Plugin.afterResponse`, so a 500 from a plugin piped later won't leave a stored row (D44).
- `@schmock/core` has a browser build, and an intercept-only browser bundle went from 251 KB to 47 KB (D53).
- GitHub Actions has never produced a run for this repository, so nothing in CI enforced ESLint, knip, the e2e suite, or the registry checks. The local release gate now runs all of them and `bun audit` (D55). The cause of the missing runs is outside the tree and still unknown.

## Before release

- Bump every package's minor version with `bump.ts`, which also moves every `@schmock/*` dependency and peer range, and publish core first. The other packages import names only the new core has: `Plugin.afterResponse`, the browser build, and the `@schmock/core/adapter` additions (`toError`, `buildJsonErrorResponse`, `isCredentialName`, `requestBodyKindOf`, `parseJsonBody`, `parseFormBody`, `HttpIngressError`). `@schmock/angular` adds `OpenApiPeer`, and openapi's callback request gains `signal`.
- Don't publish `@schmock/faker` or `@schmock/openapi` on their own. A single-package publish now refuses unless npm already serves every `@schmock/*` dependency and peer of the package at the same version (D55).
- Turn on the repository's "Dependabot security updates" setting. Without it, the new security-only `.github/dependabot.yml` does nothing.
- No release-notes file was written for this run. The user-visible changes are in D44 to D55. The ones most likely to need a changelog line are: faker rejects an unhonourable `not` at creation, so openapi answers such a response schema with `SCHEMA_VALIDATION_ERROR` (D46); a spec given as a URL loads only under an external-refs policy that allows it (D50); CRUD answers in each operation's declared envelope (D51); Express and Angular request overrides merge headers and query instead of replacing them, and Angular in strict mode refuses malformed JSON with a 400 (D52); a status tuple returning a `Date` is now labelled `application/json` (D53); the CLI refuses a blank spec and `--watch` on a spec URL; and seeded faker output changes for schemas that hold a merged reference or a `not` beside a pointer `$ref` (D46).

### Refuted by the verifiers

Kept so nobody re-raises it without new evidence.

| Id | Claim | Why it was refuted |
|---|---|---|
| adapters-7 | responseType 'json' delivers a string body unparsed, unlike every Angular backend | The behaviour is real but intended and documented. angular.md:353-356 says 'json passes the value through untouched — a route returning a pre-serialized string stays a string', and the comment at index.ts:84-91 explains why. The reviewer accepts this. The headline 'unlike every Angular backend' is wrong: Angular's own mock backend (HttpClientTestingBackend via TestRequest.flush, then _maybeConvertBody, then _toJsonBody, http-testing.mjs:108-118) returns a string body for responseType 'json' unchanged, exactly as Schmock does. Only the wire transports (XHR onLoad :1675-1685, FetchBackend.parseBody :937-947) JSON.parse it. The reviewer has a fair point that the comment's rationale ('parsing would turn true into the boolean') describes what XHR and Fetch actually do. Reversing the documented choice is a decision to make, not a defect, and it is not in REVIEW-2026-09-25 or DECISIONS.md. |
